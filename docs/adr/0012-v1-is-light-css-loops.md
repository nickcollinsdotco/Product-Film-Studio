# v1 is light: CSS 3D Loops in the Steel Hat style; Three.js and the image-quality pipeline wait

We build our own Loops, but v1 aims for passable videos that are quick, cheap and simple to make, not for beating Ultramock's image quality. The reasons to build are full Films and one consistent system per Project. v1 is CSS 3D in HyperFrames only, so ADR-0002's CSS-first decision stands and its review is closed. The guide for v1 is Nick's own Steel Hat clips (`references/own/`): flat brand-colour Backdrops, phone and laptop frames, bold tilts and moves, no depth of field and no grain. We rejected carrying the look test's Three.js version (ticket 02) into v1. It matched Ultramock's free-tier still on in-focus type, but shaped depth of field, bloom and a grain pipeline cost far more than v1 needs.

## Consequences

- **Built from Quick Loop.** v1 reuses Quick Loop's working CSS (`tools/quick-loop/`: layout, Backdrop, Device frame, scroll and focus moves) inside the Library, adding only what several Shots per Loop, reusable Shot templates and Project-level settings need. No general-purpose scene framework: the architecture is sized to the first complete Loop. Quick Loop itself stays as it is.
- **Shot templates:** Scroll and Hold. A Bookend is built from them (for example Hold, Scroll, Hold back to the opening). Others are added when a real Loop needs one.
- **Device frames:** none, browser, and phone (a PNG bezel, Y-tilt kept to about 20° so it doesn't read as cardboard; amended 2026-10-12: drawn as Nick's simple shape in CSS until real device art exists, v1-library ticket 11). No laptop: the browser frame covers desktop sites.
- **Backdrops:** brand colour, void and Backlight. The default is brand colour when the Product brand has a strong colour, otherwise Backlight.
- **Timing is time-based.** A Shot's moves are fractions of its own duration, so a Shot stretches to fit its host clip instead of freezing (this replaces ADR-0007's freeze rule for v1). Exporting at another length scales every Shot proportionally. Changing the frame rate changes neither speed nor duration.
- **Frame size is an export setting, not an Edit file.** A Loop has one source and one export command, which takes the frame size and optionally a length. Each Loop names a primary Frame size explicitly: its source previews at it in Studio, and the export uses it unless told otherwise. Presets: Landscape 16:9, Story 9:16, Square 1:1, Portrait 4:5 and Classic 4:3, all with a 1600 px long edge; custom dimensions (even numbers) when asked. Local `hyperframes render` can't override a composition's size, so the export stamps it into a temporary copy of the entry file and deletes it afterwards, as Quick Loop does.
- **Layout per ratio is simple and explicit.** Shot templates follow a few plain rules per ratio. No responsive composition engine, automatic reflow, platform-specific rendering or per-ratio choreography. A supported ratio isn't a promise that every Loop looks good in it. The first production Loop is validated at 16:9 and 9:16; other ratios get refinements only when a real Loop needs them. In portrait, a browser frame reuses Quick Loop's fill behaviour (the viewport grows to fill the height). This is provisional: if the VR website looks poor in 9:16, the fix is the smallest local adjustment.
- **60fps by default**, configurable. Before it's locked in, one representative Scroll Shot is rendered at 30 and 60fps at 1600 px and 5 Mbps and compared for smoothness, compression and render time; 60 stays unless that shows a material downside. No automatic frame-rate selection or benchmarking.
- **Seam:** ADR-0011's scene-state checks (pose, speed, no duplicate frame) plus a side-by-side image of t = D and t = 0, judged by eye. No pixel thresholds. A Tour gets no Seam check.
- **Shipping:** a Loop ships when it looks right at card size on the review page next to the Steel Hat clip and, if it's a Bookend, passes the Seam check. This replaces ADR-0010's measured sharpness rule. Amended 2026-10-14 (loops ticket 13), after the first VR Loop read as a double zoom: a Loop has one subject and at most one push-in, settles on its Notice for at least 1s, then returns; a Scroll runs at constant zoom.
- **Drafts and review:** a half-size Draft render checks composition and motion; a Loop is only shipped after a Final render at full size. Comparison with the Steel Hat clip is manual. Batch Draft renders and a review page wait until a Project has at least two Loops (first built for the VR Loops, loops ticket 13).
- **Screens from live URLs** use Quick Loop's capture (full page, cookie banners hidden), which makes ADR-0006 accepted. A pinned header is captured separately only when a real Loop needs one.
- **Delivery:** the portfolio is the main destination. Its Rendition is at most 6 MB, encoded at 5 Mbps; a Loop too long for that drops its bitrate to fit. Instagram and X get no destination-specific encoding, sizing or tests until a real post looks bad.
- **Not in v1:** depth of field, grain, bloom, motion blur, Three.js, Recordings, type, the Cursor, more than one Screen per Loop, the laptop frame, and the Drift, Reveal and Orbit Shot templates. The look test's findings (`.scratch/look-test/FINDINGS.md`: texture LOD bias −0.5, frame 0 byte-identical on one GPU, grain 0.03 surviving 4–5 Mbps where dither alone bands, 1600 against 1920) wait for the version that adds them.
- **Fallback:** Ultramock is a source of camera-move ideas, not a quality bar. If the CSS Loops aren't good enough, Loops fall back to Ultramock Pro (about $20 a month), exported as a PNG sequence so we still do our own encode.
